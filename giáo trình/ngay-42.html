Laravel: Logging, Queue và Feature Test

Mục tiêu và chuẩn bị

Quan sát ứng dụng không lộ bí mật, xử lý tác vụ nền bằng queue và viết feature test cho luồng người dùng, validation và phân quyền.

Cần PHP CLI hoạt động theo Ngày 11. Ví dụ độc lập chạy bằng PHP CLI; đoạn Laravel, Blade hoặc SQL phải đặt vào dự án và môi trường tương ứng theo chú thích.

Log phục vụ chẩn đoán

Ghi sự kiện có ngữ cảnh cần thiết như operation, ID phù hợp và trạng thái. Tránh ghi mật khẩu, token, session ID hoặc toàn bộ payload chứa dữ liệu cá nhân.

<?php
use Illuminate\Support\Facades\Log;

Log::info("Student created", ["student_id" => 123]);

Đoạn code chạy trong ứng dụng Laravel. Chọn mức log, chính sách lưu trữ và quyền đọc log phù hợp môi trường.

Queue là gì?

Queue chuyển tác vụ có thể xử lý sau, chẳng hạn gửi mail, sang worker. Request và worker có thể thất bại độc lập; thiết kế retry hữu hạn, quan sát failed jobs và tránh tác dụng phụ lặp.

Request → lưu dữ liệu → đưa job vào queue → worker xử lý

Không giả định enqueue đồng nghĩa email đã gửi. Nếu job phụ thuộc dữ liệu DB vừa ghi, cân nhắc dispatch sau commit theo cấu hình phiên bản.

Worker và driver

queue:work chạy worker sử dụng driver cấu hình. Driver sync chạy trong request; database hoặc Redis cần cấu hình và giám sát worker riêng. Dừng worker phát triển bằng Ctrl+C.

php artisan queue:work

Chỉ chạy worker khi đã biết queue connection và tài nguyên sử dụng. Không chạy queue production hay gửi mail thật trong môi trường học.

Queue mail

Mailable hoặc job có thể được đưa vào queue với cơ chế phù hợp của Laravel. Test dùng Mail::fake hoặc Queue::fake để xác nhận dự kiến mà không gửi email thật.

<?php
// Trong test Laravel, sau khi cấu hình ứng dụng.
\Illuminate\Support\Facades\Mail::fake();
// Thực hiện hành động gửi mail, sau đó assert mail được queue.

Chọn assertion phù hợp với cách dùng send hay queue. Ví dụ chỉ thể hiện fake; cần class mail và hành động thực tế để kiểm thử.

Feature test

Feature test gửi request qua các thành phần ứng dụng để kiểm tra response, DB và quyền. Dùng database thử nghiệm tách biệt; RefreshDatabase có thể làm thay đổi hoặc xóa dữ liệu trong database test cấu hình.

php artisan make:test StudentFeatureTest
php artisan test

Trước khi chạy, kiểm tra .env.testing hoặc phpunit.xml trỏ tới DB thử nghiệm, không phải dữ liệu cá nhân hay production.

Ví dụ kiểm thử response

Sau khi đã tạo route và model phù hợp, test user được phép xem danh sách. Assertion phải phù hợp response thực và thiết lập dữ liệu; không tuyên bố test chạy nếu thiếu các thành phần cần thiết.

<?php
// Bên trong một test class Laravel.
public function test_student_list_is_visible(): void {
    $user = \App\Models\User::factory()->create();
    $response = $this->actingAs($user)->get("/students");
    $response->assertOk();
}

Đoạn code cần User factory, route /students và môi trường test tương ứng. Bổ sung kiểm thử 401/403, validation 422 và dữ liệu bị từ chối không thay đổi.

Debug có hệ thống

Khi lỗi xuất hiện: tái hiện, đọc log không lộ bí mật, xác định tầng gây lỗi, tạo giả thuyết và test. Phân biệt lỗi môi trường, route, validation, quyền và database.

Request → Route → Middleware → Controller → Model/DB → Response

Không bật APP_DEBUG công khai trên production. Dùng dữ liệu test để tái hiện thay vì sao chép dữ liệu nhạy cảm.

Bài tập theo lộ trình

  1. Ghi log nghiệp vụ không lộ dữ liệu nhạy cảm và đưa mail chào mừng vào queue; kiểm tra worker và failed job trong môi trường thử nghiệm.
  2. Viết ít nhất 5 feature test: login, danh sách, tạo hợp lệ, tạo lỗi 422 và user thường bị chặn xóa 403; kiểm tra database test trước khi chạy.
  3. Hoàn thiện mini test ứng dụng Laravel sinh viên có Web, REST API, Auth, Upload và Tests; chỉ công khai hoặc triển khai khi được yêu cầu.

Ghi đầu vào, kết quả mong đợi và thực tế; kiểm tra cả trường hợp rỗng và biên.
