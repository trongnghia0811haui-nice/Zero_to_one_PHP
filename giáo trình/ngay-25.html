MySQL: Index, Constraints và chuẩn hóa

Mục lục← Ngày 24Ngày 26 →

Mục tiêu và chuẩn bị

Thiết kế ràng buộc dữ liệu, xem xét quan hệ và chuẩn hóa 1NF–3NF; tạo index dựa trên truy vấn và dùng EXPLAIN để quan sát kế hoạch.

Thực hành trên cơ sở dữ liệu MySQL thử nghiệm riêng, không dùng dữ liệu quan trọng. Chuẩn bị schema từ bài trước khi chạy các truy vấn liên quan.

Ràng buộc dữ liệu

PRIMARY KEY, FOREIGN KEY, UNIQUE, NOT NULL và CHECK giúp database từ chối trạng thái không hợp lệ. Validation phía ứng dụng vẫn cần thiết để thông báo lỗi rõ ràng và kiểm tra quy tắc nghiệp vụ.

CREATE TABLE example_scores (
    id INT PRIMARY KEY AUTO_INCREMENT,
    score DECIMAL(4,2) NOT NULL,
    CONSTRAINT chk_example_score CHECK (score >= 0 AND score <= 10)
) ENGINE=InnoDB;

Chạy trong database thử nghiệm MySQL 8.0.16 trở lên để CHECK được thực thi; không giả định mọi phiên bản MySQL hoặc hệ quản trị có cùng hành vi.

UNIQUE và khóa ngoại

UNIQUE ngăn giá trị hoặc tổ hợp trùng theo quy tắc cột và collation; khóa ngoại bảo đảm tham chiếu. Quyết định ON DELETE cần phản ánh nghiệp vụ và ảnh hưởng dữ liệu.

-- Chỉ thêm nếu các ràng buộc chưa tồn tại.
ALTER TABLE scores
  ADD CONSTRAINT uq_student_subject UNIQUE (student_id, subject_id);
ALTER TABLE scores
  ADD CONSTRAINT chk_score_range CHECK (score >= 0 AND score <= 10);

Schema mẫu Ngày 21 đã có UNIQUE(student_id, subject_id); không chạy lặp constraint này. Kiểm tra dữ liệu hiện tại và tên constraint trước khi thay đổi.

Index là gì?

Index là cấu trúc hỗ trợ truy cập dữ liệu theo khóa. Nó có thể giúp lọc, nối và sắp xếp, nhưng cũng tốn dung lượng và chi phí khi ghi; optimizer có thể chọn không dùng index.

CREATE INDEX idx_students_name ON students(name);
EXPLAIN SELECT id, name FROM students WHERE name = 'An';

Chỉ tạo trong database thử nghiệm và kiểm tra xem index đã tồn tại chưa. So sánh kế hoạch và thời gian trên dữ liệu đại diện, không kết luận chỉ từ một lần chạy.

Khóa ngoại và index đã có

MySQL/InnoDB có thể tự tạo index hỗ trợ khóa ngoại nếu chưa có index phù hợp. Tạo index trùng lặp thường làm tăng chi phí mà không thêm lợi ích; kiểm tra trước bằng SHOW INDEX.

SHOW INDEX FROM students;
SHOW INDEX FROM scores;

Đặc biệt kiểm tra students.class_id và scores.student_id. Index tổ hợp UNIQUE(student_id, subject_id) thường đã hỗ trợ tìm theo student_id ở vị trí đầu.

EXPLAIN

EXPLAIN mô tả kế hoạch mà optimizer dự kiến dùng. Các cột như key và rows giúp hình thành giả thuyết, không phải số đo thời gian thực; kết quả thay đổi theo dữ liệu, thống kê và phiên bản.

EXPLAIN SELECT id, name
FROM students
WHERE class_id = 1
ORDER BY name;

Đo trước/sau trên cùng dữ liệu đại diện; dùng công cụ đo phù hợp và xem toàn bộ kế hoạch. Không hứa chắc một index luôn cải thiện hiệu năng.

Chuẩn hóa 1NF, 2NF, 3NF

1NF yêu cầu giá trị thuộc tính phù hợp dạng nguyên tử theo mô hình; 2NF loại phụ thuộc bộ phận của thuộc tính không khóa vào khóa ứng viên; 3NF xử lý phụ thuộc bắc cầu không phù hợp. Phân tích phụ thuộc hàm và khóa ứng viên của chính nghiệp vụ.

classes(id, class_name, description)
students(id, name, email, phone, class_id)
subjects(id, subject_name, credits)
scores(id, student_id, subject_id, score)

Đây là sơ đồ định hướng, không tự chứng minh 3NF. Cần xác định phụ thuộc hàm và giả định nghiệp vụ, ví dụ một email có thực sự duy nhất không.

Thiết kế users

Tạo bảng users với email duy nhất và hash mật khẩu, không lưu plaintext. Dùng một cột password đủ dài cho hash và xử lý quyền ở ứng dụng; tên bảng và schema chỉ là ví dụ.

CREATE TABLE users (
 id INT AUTO_INCREMENT PRIMARY KEY,
 name VARCHAR(150) NOT NULL,
 email VARCHAR(255) NOT NULL UNIQUE,
 password VARCHAR(255) NOT NULL,
 role VARCHAR(30) NOT NULL DEFAULT 'member'
) ENGINE=InnoDB;

Không chèn mật khẩu thật vào tệp ví dụ. password_hash/password_verify xử lý mật khẩu trong PHP; validation và authorization phải thực hiện phía server.

Bài tập theo lộ trình

  1. Phân tích phụ thuộc hàm, khóa ứng viên và 1NF–3NF của bốn bảng; kiểm tra dữ liệu hiện tại trước khi thêm ràng buộc.
  2. Kiểm tra SHOW INDEX, tạo index phù hợp trên bản thử nghiệm và so sánh EXPLAIN trước/sau; tránh tạo trùng index do FK hoặc UNIQUE đã có.
  3. Tạo bảng users, kiểm tra email trùng và lưu hash mật khẩu; ghi lại tác động và lựa chọn khôi phục trước thay đổi schema.

Ghi đầu vào, kết quả mong đợi và thực tế; kiểm tra cả trường hợp rỗng và biên.

Tự kiểm tra và tổng kết

  • Tự giải thích từng khái niệm và chạy lại các ví dụ.
  • Hoàn thành bài tập và xử lý dữ liệu biên, dữ liệu sai.
  • So sánh kết quả thực tế với kết quả dự đoán và ghi lại lỗi.

Tham khảo MySQL Manual và PHP Manual, chọn đúng phiên bản đang dùng.
