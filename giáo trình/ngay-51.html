Task Management: Giao việc, trạng thái và deadline

Mục lục← Ngày 50Ngày 52 →

Mục tiêu và chuẩn bị

Giao task cho thành viên hợp lệ, thay đổi trạng thái theo quy tắc và hiển thị công việc cá nhân theo deadline.

Cần PHP CLI hoạt động theo Ngày 11. Ví dụ độc lập chạy bằng PHP CLI; đoạn Laravel, Blade hoặc SQL phải đặt vào dự án và môi trường tương ứng theo chú thích.

Assignment và thành viên

Một task có thể được giao cho nhiều user qua task_assignments. Mỗi người được giao phải thuộc project của task theo yêu cầu; kiểm tra tại server cho từng user ID.

task → project_id
project_members(project_id, user_id) → kiểm tra thành viên
task_assignments(task_id, user_id) → lưu quan hệ

Khóa ngoại vào users và tasks chưa tự đảm bảo thành viên cùng project. Dùng unique(task_id,user_id) để chặn trùng.

Validate danh sách người nhận

Kiểm tra input là mảng, mỗi ID hợp lệ, không trùng và user tồn tại. Tiếp tục đối chiếu tập ID với thành viên dự án và kiểm tra quyền người thực hiện.

<?php
// Rules trong Form Request Laravel.
return [
    "assignees" => ["required", "array"],
    "assignees.*" => ["integer", "distinct", "exists:users,id"],
];

Rule exists chỉ kiểm tra user tồn tại, chưa kiểm tra membership. Quyết định có cho phép mảng rỗng để gỡ toàn bộ assignment hay không.

sync và tác động thay thế

sync thay thế toàn bộ quan hệ bằng danh sách ID cung cấp; ID không có trong danh sách có thể bị gỡ. syncWithoutDetaching thêm mà giữ quan hệ cũ; chọn phương thức phù hợp yêu cầu.

<?php
// Sau authorization và kiểm tra mọi ID thuộc project.
$task->assignees()->sync($validatedIds);

Thao tác trong transaction khi nhiều bước cần nhất quán. Xử lý cạnh tranh nếu một member bị gỡ khỏi project cùng lúc.

Chuyển trạng thái

Định nghĩa rõ các trạng thái và ai được phép chuyển. Nếu quy trình chỉ cho todo → in_progress → done, kiểm tra chuyển tiếp ở server thay vì tin nút giao diện.

todo → in_progress → done
Yêu cầu đổi trạng thái → authorize → validate transition → lưu

Ví dụ trình tự là đề xuất; nếu sản phẩm cho chuyển ngược, ghi rõ quy tắc và kiểm thử trường hợp đó.

Xác định task quá hạn

Quá hạn thường là deadline đã qua và task chưa done. Nếu deadline là kiểu date, cần quyết định so với ngày hiện tại trong múi giờ nghiệp vụ; nếu là datetime, so sánh thời điểm.

Ví dụ theo ngày: due_date < ngày hôm nay VÀ status != done

Nếu due_date NULL, không tự đánh dấu quá hạn trừ khi chính sách yêu cầu. Dùng chữ hoặc biểu tượng cùng màu để trạng thái dễ nhận biết.

Công việc của tôi

Lọc task qua assignment của user hiện tại và áp dụng quyền project; sắp xếp theo deadline, quy định vị trí deadline NULL, phân trang và tránh N+1.

GET /my-tasks → task được giao cho user hiện tại
Sắp xếp theo deadline gần nhất, có tiêu chí ID phụ

Không lấy mọi task rồi lọc ở trình duyệt. Quyết định người đã bị gỡ khỏi project còn nhìn thấy assignment hay không.

Kiểm thử cạnh tranh và dữ liệu biên

Test ID không tồn tại, user ngoài project, ID trùng, mảng rỗng, sync làm gỡ quan hệ cũ, task done quá hạn và deadline hôm nay/quá khứ/tương lai.

Case: gán user ngoài project → từ chối, không thay đổi assignment
Case: task done, deadline hôm qua → không đánh dấu quá hạn

Dùng database thử nghiệm và xác nhận dữ liệu sau request bị từ chối, không chỉ kiểm tra status.

Bài tập theo lộ trình

  1. Giao task cho một hoặc nhiều thành viên thuộc project; validate ID, bảo vệ quyền, lưu quan hệ bằng sync theo hợp đồng.
  2. Triển khai đổi nhanh trạng thái và nhận diện quá hạn; test quy tắc chuyển tiếp, múi giờ, due_date NULL và task đã hoàn thành.
  3. Tạo /my-tasks chỉ hiển thị task hợp lệ của user hiện tại, sắp xếp deadline và phân trang; test user bị gỡ khỏi project.

Ghi đầu vào, kết quả mong đợi và thực tế; kiểm tra cả trường hợp rỗng và biên.

Tự kiểm tra và tổng kết

  • Tự giải thích từng khái niệm và chạy lại các ví dụ.
  • Hoàn thành bài tập và xử lý dữ liệu biên, dữ liệu sai.
  • So sánh kết quả thực tế với kết quả dự đoán và ghi lại lỗi.
