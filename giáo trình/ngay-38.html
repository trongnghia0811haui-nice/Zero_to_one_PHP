Laravel: Request Validation và Form Request

Mục tiêu và chuẩn bị

Xác thực dữ liệu tạo/sửa sinh viên, kiểm tra quyền trong Form Request, xử lý unique khi cập nhật và hiển thị lỗi có thể sử dụng.

Cần PHP CLI hoạt động theo Ngày 11. Ví dụ độc lập chạy bằng PHP CLI; đoạn Laravel, Blade hoặc SQL phải đặt vào dự án và môi trường tương ứng theo chú thích.

Validation ở server

HTML validation cải thiện trải nghiệm nhưng có thể bị bỏ qua; server phải kiểm tra kiểu, trường bắt buộc, độ dài, định dạng và ràng buộc nghiệp vụ trước khi lưu.

<?php
// Trong controller Laravel:
$data = $request->validate([
    "name" => ["required", "string", "max:150"],
    "email" => ["required", "email", "max:255"],
]);

Đoạn này cần Request hợp lệ. Laravel thường redirect về form khi validation web thất bại hoặc trả JSON 422 khi request mong đợi JSON.

Tạo Form Request

Form Request giúp đặt rules, messages và authorize trong một lớp riêng. Sinh bằng Artisan trong dự án thử nghiệm, sau đó kiểm tra file đã có trước khi tạo.

php artisan make:request StoreStudentRequest
php artisan make:request UpdateStudentRequest

Không ghi đè lớp đang tồn tại. Nội dung sinh ra có thể khác theo phiên bản Laravel, hãy đọc file và tài liệu tương ứng.

Quy tắc tạo mới

Các quy tắc required, string, email, unique và exists có thể kết hợp thành mảng. Bảng/cột phải khớp schema; tồn tại trong DB không có nghĩa người dùng có quyền dùng bản ghi đó.

<?php
// Bên trong StoreStudentRequest::rules()
return [
    "name" => ["required", "string", "max:150"],
    "email" => ["required", "email", "unique:students,email"],
    "class_id" => ["required", "integer", "exists:classes,id"],
];

Đây là nội dung phương thức, cần class Form Request và schema phù hợp. Luôn cân nhắc kiểm tra quyền trên lớp được chọn.

Unique khi cập nhật

Khi sửa, email của chính sinh viên không nên bị coi là trùng. Rule::unique()->ignore() cần nhận model đã xác định đáng tin cậy, không ghép trực tiếp giá trị request vào câu SQL.

<?php
use Illuminate\Validation\Rule;

// Trong UpdateStudentRequest::rules(); route model binding cung cấp student.
return [
    "email" => ["required", "email", Rule::unique("students", "email")->ignore($this->route("student"))],
];

Route binding phải cung cấp model phù hợp; không dùng giá trị tùy ý từ người dùng trong ignore. Xác định chính sách với bản ghi xóa mềm theo nghiệp vụ.

authorize và policy

Form Request authorize quyết định user có được yêu cầu hành động không; policy mô tả quyền đối với tài nguyên. Validation đúng định dạng không đồng nghĩa được phép sửa.

<?php
// Trong UpdateStudentRequest::authorize().
public function authorize(): bool {
    $student = $this->route("student");
    return $this->user()?->can("update", $student) ?? false;
}

Cần cấu hình xác thực, policy và route binding phù hợp. Dữ liệu thiếu hoặc user chưa đăng nhập cần được xử lý theo hợp đồng ứng dụng.

Thông báo lỗi và old input

messages() cho phép thông báo tiếng Việt. Trong Blade, @error đọc lỗi từng trường; old() khôi phục input không nhạy cảm sau redirect. Không in hoặc điền lại mật khẩu.

<?php
// Bên trong Form Request.
public function messages(): array {
    return ["email.email" => "Email không đúng định dạng.",
            "name.required" => "Vui lòng nhập họ tên."];
}

Gắn label, thông báo và trạng thái lỗi phù hợp. Cần thử bằng bàn phím và trình đọc màn hình khi hoàn thiện giao diện.

Kiểm thử các nhánh

Kiểm tra thiếu trường, sai kiểu, sai định dạng, email trùng khi tạo, email của chính bản ghi khi cập nhật và email trùng bản ghi khác. Test cả user không có quyền.

Thiếu name → lỗi validation
Email sai → lỗi validation
Update giữ email cũ → hợp lệ nếu có quyền
Update dùng email của người khác → lỗi unique
User không đủ quyền → 403 theo chính sách

Trong API JSON, validation failure thường trả 422; với web, Laravel thường redirect và gắn lỗi vào session. Hãy kiểm tra response thực tế.

Bài tập theo lộ trình

  1. Tạo StoreStudentRequest và UpdateStudentRequest với required, email, unique, exists; khi cập nhật bỏ qua đúng model đang sửa.
  2. Viết messages tiếng Việt, hiển thị @error và old() cho dữ liệu không nhạy cảm; cấu hình policy và authorize.
  3. Viết test thiếu trường, sai email, trùng khi tạo, giữ email cũ khi sửa, trùng email của người khác và trường hợp 403.

Ghi đầu vào, kết quả mong đợi và thực tế; kiểm tra cả trường hợp rỗng và biên.
