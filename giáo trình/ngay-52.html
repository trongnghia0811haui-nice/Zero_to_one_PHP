Task Management: Dashboard, thống kê và API

Mục tiêu và chuẩn bị

Tổng hợp dữ liệu đúng phạm vi quyền, tính số task theo trạng thái và quá hạn, thiết kế dữ liệu biểu đồ và endpoint dashboard.

Chuẩn bị bản ghi chú, sơ đồ và dự án thử nghiệm. Ví dụ minh họa phải được điều chỉnh theo yêu cầu và môi trường thực tế.

Dashboard trả lời câu hỏi gì?

Xác định người xem và phạm vi trước khi tính: tổng project, tổng task, số lượng theo trạng thái, quá hạn và năm task sắp tới hạn. User khác nhau có thể nhìn thấy số liệu khác nhau.

User → tập project được phép → task thuộc các project đó → thống kê

Không trả tổng toàn hệ thống cho member nếu họ chỉ được xem một số dự án.

Đếm theo trạng thái

Lọc tập task hợp lệ trước rồi GROUP BY status. Nếu muốn biểu đồ luôn có đủ trạng thái kể cả số 0, ghép danh sách trạng thái chuẩn với kết quả truy vấn.

SELECT status, COUNT(*) AS total
FROM tasks
WHERE project_id = 1
GROUP BY status;

SQL ví dụ dùng project_id cố định trong DB thử nghiệm. Trong ứng dụng, dùng tham số và scope authorization; cần xác định trạng thái hợp lệ.

Quá hạn và sắp đến hạn

Quy định ngày hiện tại theo múi giờ nghiệp vụ. Quá hạn theo ngày thường là due_date trước hôm nay và status khác done; task không có due_date cần xử lý riêng.

Quá hạn: due_date < hôm nay và status != done
Sắp tới hạn: task chưa xong có deadline hợp lệ, theo thứ tự gần nhất

Khi tính top 5, xác định có bao gồm task đã quá hạn hay không, cách xử lý deadline hôm nay và thứ tự khi trùng.

Tránh đếm trùng

JOIN với project_members hoặc task_assignments có thể nhân số dòng khi một task có nhiều assignee. Dùng EXISTS, subquery hoặc COUNT DISTINCT tùy nghiệp vụ và kiểm thử dữ liệu nhiều quan hệ.

Một task có hai assignee sau JOIN có thể tạo hai dòng.
Đếm task cần chú ý COUNT(DISTINCT tasks.id).

DISTINCT không tự sửa mọi lỗi thiết kế query. Kiểm tra tập dữ liệu và kết quả mong muốn trước khi tối ưu.

Dữ liệu cho biểu đồ

Biểu đồ cần labels và số liệu cùng thứ tự. Trạng thái rỗng, dữ liệu 0 và lỗi API nên có thông báo bằng chữ; không phụ thuộc chỉ vào màu.

labels: ["Todo", "In Progress", "Done"]
values: [3, 2, 5]

Nếu dùng Chart.js, chọn phiên bản phù hợp và theo tài liệu chính thức; không nhúng dữ liệu không tin cậy vào script bằng cách nối chuỗi tùy ý.

Endpoint summary

Endpoint /api/dashboard/summary cần xác thực và phạm vi quyền giống web. Chỉ trả trường cần thiết, số liệu có kiểu dữ liệu rõ ràng và không tiết lộ project user không được xem.

{"total_projects":2,"total_tasks":10,"by_status":{"todo":3,"in_progress":2,"done":5}}

JSON là ví dụ dữ liệu giả. Quy định xử lý lỗi và status; tránh công bố mật khẩu, token hoặc thông tin nhạy cảm.

Đối chiếu và kiểm thử

Tạo dữ liệu thử có hai user nhìn thấy các project khác nhau; tự đếm để đối chiếu API và giao diện. Thử dữ liệu rỗng, nhiều assignee, task done, quá hạn và deadline null.

User A: thấy Project A → dashboard chỉ tính task A
User B: không thuộc A → không được thấy số liệu chi tiết A

Kiểm tra response API trực tiếp và query, không chỉ nhìn biểu đồ. Đo số query khi có nhiều bản ghi để phát hiện N+1.

Bài tập theo lộ trình

  1. Viết truy vấn tổng project/task, theo status, quá hạn và top 5 deadline; xác định phạm vi quyền và quy tắc ngày.
  2. Tạo biểu đồ status/priority, xử lý 0 dữ liệu, lỗi API và cung cấp phần mô tả văn bản.
  3. Tạo GET /api/dashboard/summary; đối chiếu số liệu với DB test cho nhiều user và trường hợp task có nhiều assignee.

Ghi đầu vào, kết quả mong đợi và thực tế; kiểm tra cả trường hợp rỗng và biên.

Tự kiểm tra và tổng kết

  • Tự giải thích từng khái niệm và chạy lại các ví dụ.
  • Hoàn thành bài tập và xử lý dữ liệu biên, dữ liệu sai.
  • So sánh kết quả thực tế với kết quả dự đoán và ghi lại lỗi.
