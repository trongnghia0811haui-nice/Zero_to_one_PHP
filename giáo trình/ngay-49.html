Task Management: Thành viên dự án

Mục tiêu và chuẩn bị

Thêm, xem và xóa thành viên an toàn; ngăn trùng, bảo vệ owner và xử lý các task đã giao khi quyền thành viên thay đổi.

Cần PHP CLI hoạt động theo Ngày 11. Ví dụ độc lập chạy bằng PHP CLI; đoạn Laravel, Blade hoặc SQL phải đặt vào dự án và môi trường tương ứng theo chú thích.

Quan hệ users và projects

Project và user là quan hệ nhiều-nhiều qua project_members. Cột project_id và user_id cần khóa ngoại và UNIQUE theo cặp để tránh trùng ở mức database.

projects 1 ── N project_members N ── 1 users
UNIQUE(project_id, user_id)

Khóa unique quan trọng ngay cả khi giao diện đã kiểm tra: hai request đồng thời có thể cùng vượt qua bước kiểm tra ban đầu.

Thêm thành viên

Xác minh người gọi có quyền quản lý member, user được thêm tồn tại và project đúng phạm vi. Quyết định API trả lỗi hay thành công idempotent khi thành viên đã có.

Yêu cầu: POST /projects/{project}/members
Kiểm tra: user_id tồn tại và người gọi có quyền
Ghi: thêm cặp project_id + user_id
Kết quả: theo hợp đồng API

Đây là luồng minh họa, chưa phải endpoint đã chạy. Không tin role, project_id hoặc owner_id tùy ý từ client.

Validation và ràng buộc

Rule exists có thể kiểm tra user tồn tại; policy phải kiểm tra người gọi có quyền. UNIQUE trong database xử lý request cạnh tranh; bắt lỗi trùng phù hợp mà không che lỗi khác.

<?php
// Trong Form Request Laravel.
return ["user_id" => ["required", "integer", "exists:users,id"]];

exists không chứng minh người gọi được phép thêm user đó vào project. Ràng buộc dữ liệu và authorization là các kiểm tra riêng.

attach và syncWithoutDetaching

Quan hệ belongsToMany có attach để thêm; syncWithoutDetaching thêm ID mà không loại các thành viên khác. Kiểm tra hành vi và ràng buộc theo phiên bản; không giả định thao tác giao diện đủ ngăn trùng.

<?php
// Sau authorization, validation và xử lý cạnh tranh phù hợp.
$project->members()->syncWithoutDetaching([$userId]);

Đoạn trích cần quan hệ members và project. DB vẫn cần unique(project_id,user_id); quyết định thông báo khi đã là thành viên.

Xóa thành viên và bảo vệ owner

Chặn xóa owner theo yêu cầu. Việc gỡ member cần định nghĩa cách xử lý assignment liên quan: gỡ giao việc, chuyển việc hoặc chặn xóa, tùy chính sách đã thống nhất.

Kiểm tra quyền → kiểm tra không phải owner
→ xử lý assignment của member trong project
→ xóa quan hệ member → commit

Các thao tác liên quan nên được thực hiện nhất quán trong transaction. Đề phòng request đồng thời giao task khi đang xóa member.

Danh sách và số task

Khi hiển thị số task của thành viên, chỉ đếm task của project đang xem và theo chính sách trạng thái. Tránh đếm task của dự án khác hoặc N+1 truy vấn.

Member A: 2 task trong Project X
Member A: 3 task trong Project Y
Trang Project X chỉ hiển thị 2

Định nghĩa rõ đếm tất cả task hay chỉ task đang thực hiện; kiểm thử user không có task và dữ liệu nhiều dự án.

Các ca kiểm thử

Test thêm thành công, user không tồn tại, user trùng, không có quyền, owner bị gỡ và xử lý assignment. Kiểm tra kết quả DB sau rollback hoặc khi bị từ chối.

Người ngoài project thêm member → từ chối
Thêm cùng user hai lần → không có cặp trùng
Gỡ owner → từ chối
Gỡ member → assignment xử lý theo chính sách

Nếu cần kiểm thử đồng thời, dùng database thử nghiệm riêng và không gây ảnh hưởng dữ liệu khác.

Bài tập theo lộ trình

  1. Tạo giao diện và API thêm thành viên; validate user tồn tại, kiểm tra quyền, ngăn trùng và định nghĩa response khi đã tồn tại.
  2. Xây dựng xóa thành viên: chặn xóa owner và xử lý assignment liên quan theo chính sách trong transaction phù hợp.
  3. Hiển thị danh sách thành viên và số task trong project hiện tại; kiểm tra user không có task, dự án khác và request cạnh tranh.

Ghi đầu vào, kết quả mong đợi và thực tế; kiểm tra cả trường hợp rỗng và biên.

Tự kiểm tra và tổng kết

  • Hoàn thành bài tập và xử lý dữ liệu biên, dữ liệu sai.
  • So sánh kết quả thực tế với kết quả dự đoán và ghi lại lỗi.
