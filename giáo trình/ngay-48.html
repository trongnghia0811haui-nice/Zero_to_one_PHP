Task Management: CRUD Project

Mục tiêu và chuẩn bị

Thiết kế luồng tạo, xem, sửa, xóa project cho web và API; giới hạn danh sách theo quyền và giữ tính nhất quán khi tạo owner/member.

Cần PHP CLI hoạt động theo Ngày 11. Ví dụ độc lập chạy bằng PHP CLI; đoạn Laravel, Blade hoặc SQL phải đặt vào dự án và môi trường tương ứng theo chú thích.

Hợp đồng CRUD

Một project có tên, mô tả, chủ sở hữu và thành viên. Xác định route, validation, quyền, response và tác động xóa trước khi triển khai controller hoặc service.

GET /projects → danh sách
POST /projects → tạo
GET /projects/{id} → chi tiết
PUT/PATCH /projects/{id} → sửa
DELETE /projects/{id} → xóa

Với form HTML, dùng POST kèm method spoofing và CSRF; API theo method/status đã thống nhất.

Form Request và trường được phép

StoreProjectRequest và UpdateProjectRequest xác nhận các trường người dùng được phép nhập. owner_id lấy từ user đã xác thực ở server, không tin giá trị do client gửi.

<?php
// Trong rules() của Form Request.
return [
    "name" => ["required", "string", "max:255"],
    "description" => ["nullable", "string"],
];

Sau validate vẫn phải kiểm tra quyền tạo hoặc sửa. Không mass assign role hay owner_id từ request thô.

Transaction tạo project và owner

Project mới và quan hệ owner trong project_members phải cùng được ghi hoặc cùng rollback nếu có lỗi. DB::transaction xử lý rollback khi exception thoát callback.

<?php
// Trong service Laravel; quan hệ members() đã định nghĩa.
$project = DB::transaction(function () use ($data, $user) {
    $project = Project::create(["name" => $data["name"], "owner_id" => $user->id]);
    $project->members()->attach($user->id);
    return $project;
});

Đây là đoạn trích, cần import DB/Project và validation; nếu attach lỗi, transaction phải rollback project. Không chạy trên dữ liệu ngoài môi trường thử nghiệm.

Danh sách theo quyền

Không lấy mọi project rồi chỉ ẩn giao diện. Query phải giới hạn theo owner, member hoặc admin theo ma trận quyền, trước khi phân trang và tính thống kê.

User → tập project được phép → lọc → thống kê → phân trang → response

Chính sách admin có được xem toàn bộ hay không cần được quyết định rõ. Đảm bảo API và web dùng cùng quy tắc.

Thành viên và phần trăm hoàn thành

Đếm task done và tổng task trong phạm vi project. Quy định dự án không có task trả 0% hay hiển thị chưa có dữ liệu; tránh chia cho 0 và làm rõ cách làm tròn.

Ví dụ: 3 task Done / 4 task = 75%
Không có task → quy ước hiển thị 0% hoặc N/A

Không nhân bản số dòng do JOIN nhiều bảng trung gian. Dùng withCount hoặc truy vấn tổng hợp và kiểm thử với dữ liệu nhiều thành viên.

Sửa và xóa

Lấy project theo ID, xác nhận quyền và validate. Khi xóa, hiểu khóa ngoại và các task/assignment bị ảnh hưởng; chính sách có thể yêu cầu xác nhận và ngăn xóa hoặc lưu trữ.

Request → tìm project → authorize → validate → cập nhật/xóa → response

Hộp xác nhận là hỗ trợ UI; nó không thay thế kiểm tra quyền, CSRF và kiểm tra dữ liệu.

Kiểm thử các nhánh

Test tạo thành công và cố tình gây lỗi thêm owner để xác nhận không còn project dang dở; test user ngoài dự án không xem/sửa, dữ liệu không đổi sau 403.

Case: tạo project + member thất bại → rollback
Case: project rỗng → không chia cho 0
Case: user khác truy cập → từ chối

Dùng database thử nghiệm riêng và kiểm tra trạng thái thực tế; không chỉ kiểm tra status response.

Bài tập theo lộ trình

  1. Tạo ProjectService, StoreProjectRequest, UpdateProjectRequest, ProjectController và API controller theo nhu cầu; định nghĩa quyền rõ ràng.
  2. Hoàn thiện danh sách theo phạm vi truy cập, đếm thành viên, phần trăm hoàn thành; thử project không có task và nhiều thành viên.
  3. Tạo project và gắn owner trong transaction; kiểm tra rollback khi attach thất bại, CRUD và truy cập trái phép.

Ghi đầu vào, kết quả mong đợi và thực tế; kiểm tra cả trường hợp rỗng và biên.

Tự kiểm tra và tổng kết

  • Tự giải thích từng khái niệm và chạy lại các ví dụ.
  • Hoàn thành bài tập và xử lý dữ liệu biên, dữ liệu sai.
  • So sánh kết quả thực tế với kết quả dự đoán và ghi lại lỗi.
