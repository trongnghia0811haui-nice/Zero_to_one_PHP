Task Management: Kiểm thử, SQL và bảo mật

Mục tiêu và chuẩn bị

Xây dựng bộ feature test có ý nghĩa, kiểm tra ranh giới quyền, đánh giá truy vấn và rà soát các lỗi bảo mật gắn với sản phẩm.

Cần PHP CLI hoạt động theo Ngày 11. Ví dụ độc lập chạy bằng PHP CLI; đoạn Laravel, Blade hoặc SQL phải đặt vào dự án và môi trường tương ứng theo chú thích.

Xây dựng ma trận kiểm thử

Liệt kê chức năng, vai trò, dữ liệu đầu vào và kết quả mong đợi. Ưu tiên auth, project/task, assignment, filter, phân trang và API; mỗi trường hợp cần kiểm tra response lẫn trạng thái database.

Owner sửa project của mình → cho phép
Member ngoài project sửa → từ chối, dữ liệu không đổi
Dữ liệu sai → 422 hoặc redirect theo hợp đồng

Dùng tài khoản và DB thử nghiệm riêng. Số lượng test chỉ là mức tối thiểu, không thay thế chất lượng các kịch bản.

Feature test và database test

Feature test chạy request qua nhiều thành phần Laravel. RefreshDatabase và các thao tác tạo/xóa bảng ảnh hưởng database cấu hình cho test; xác nhận .env.testing/phpunit.xml trỏ vào DB có thể xóa.

php artisan test

Không chạy test phá hủy dữ liệu trên production hay database cá nhân quan trọng. Fake mail, storage hoặc queue khi test không cần gửi thật.

Kiểm thử authorization

Tạo ít nhất owner, member và người ngoài project. Thử thay ID và gửi request trực tiếp tới web/API, kiểm tra status theo hợp đồng và DB không đổi sau khi bị từ chối.

User ngoài Project A → PUT /projects/A → 403 hoặc 404 theo chính sách
Kiểm tra name trong DB vẫn giữ nguyên

Không đánh giá bảo mật chỉ bằng việc nút bị ẩn. Kiểm tra cả truy vấn danh sách, dashboard, search và pagination.

Rà soát XSS, CSRF và dữ liệu nhạy cảm

Blade {{ }} escape mặc định; đầu ra HTML thô cần được kiểm soát. Form web thay đổi dữ liệu cần CSRF protection; API và cookie/session có ranh giới bảo mật khác nhau.

{{ $task->title }}  // Blade escape mặc định
@csrf               // Trong form web phù hợp

Không trả password hash, token hoặc cấu hình nội bộ trong API và log. Escape đầu ra tùy ngữ cảnh; không dùng htmlspecialchars thay prepared statement.

Mass assignment và validation

Chỉ cho phép trường được sửa và dùng dữ liệu đã validate. Server tự quyết định owner_id, project_id theo quan hệ được authorize; role không lấy tùy ý từ client.

Input client → validate → authorize → chỉ gán trường được phép

Thứ tự validate/authorize phụ thuộc tổ chức ứng dụng; cả hai phải xảy ra trước thay đổi dữ liệu. DB constraints bảo vệ tính nhất quán.

EXPLAIN và hiệu năng

Xác định query có vấn đề, dữ liệu đại diện và chỉ số cần đo trước. EXPLAIN giúp xem kế hoạch dự kiến; so sánh trước/sau trên cùng điều kiện và kiểm tra N+1.

EXPLAIN SELECT id, title FROM tasks WHERE project_id = 1 AND status = 'todo';

Đây là truy vấn ví dụ trên DB thử nghiệm. Index có chi phí ghi; không tuyên bố cải thiện nếu chưa đo hoặc so sánh có ý nghĩa.

Refactor an toàn

Di chuyển logic dài sang service/FormRequest khi có trách nhiệm rõ ràng; giữ hợp đồng API và chạy lại các test quan trọng sau mỗi thay đổi.

Test hiện trạng → thay đổi nhỏ → chạy test → xem diff

Không tái cấu trúc hàng loạt ngoài mục tiêu bài tập. Ghi bug, bước tái hiện và kết quả xác minh.

Bài tập theo lộ trình

  1. Viết tối thiểu 10 feature test bao phủ auth, quyền 403, CRUD project/task, assignment, lọc, phân trang và API; kiểm tra DB test trước khi chạy.
  2. Rà soát XSS, CSRF, fillable, dữ liệu nhạy cảm trong JSON và query; dùng EXPLAIN trên dữ liệu test đại diện.
  3. Sửa bug được phát hiện, refactor khi có lý do, chạy lại test liên quan và ghi kết quả thực tế.

Ghi đầu vào, kết quả mong đợi và thực tế; kiểm tra cả trường hợp rỗng và biên.

Tự kiểm tra và tổng kết

  • Tự giải thích từng khái niệm và chạy lại các ví dụ.
  • Hoàn thành bài tập và xử lý dữ liệu biên, dữ liệu sai.
  • So sánh kết quả thực tế với kết quả dự đoán và ghi lại lỗi.

Tham khảo MySQL Manual và PHP Manual, chọn đúng phiên bản đang dùng.
