Mục tiêu và chuẩn bị

Thiết kế API sinh viên với method, status code và dữ liệu JSON rõ ràng; kiểm thử các trường hợp thành công, sai đầu vào và không tìm thấy.

Cần PHP CLI hoạt động theo Ngày 11. Ví dụ độc lập chạy bằng PHP CLI; đoạn Laravel, Blade hoặc SQL phải đặt vào dự án và môi trường tương ứng theo chú thích.

HTTP request và response

Request gồm method, path, headers và có thể có body. Response gồm status, headers và body. Client cần dựa vào hợp đồng API thay vì giả định mọi lỗi đều là 200.

GET /api/students HTTP/1.1
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{"data": []}

Đây là ví dụ mô phỏng thông điệp, không phải lệnh terminal. Server thực tế cần thiết lập header và status phù hợp.

Thiết kế tài nguyên

REST API thường biểu diễn sinh viên bằng tài nguyên /api/students. GET đọc; POST tạo; PUT cập nhật toàn bộ biểu diễn theo hợp đồng; DELETE yêu cầu xóa. Xác thực danh tính và kiểm tra quyền là hai bước khác nhau.

GET    /api/students
POST   /api/students
GET    /api/students/1
PUT    /api/students/1
DELETE /api/students/1

Thiết kế rõ field bắt buộc, phương thức được phép và hành vi lặp request. Việc dùng PUT không tự bảo đảm mọi tác dụng phụ đều idempotent.

Status code thông dụng

200 thường cho request thành công, 201 cho tạo mới, 400 cho request sai cú pháp hoặc không hợp lệ theo hợp đồng, 404 không tìm thấy; 422 cho dữ liệu đúng cú pháp nhưng không đạt quy tắc validation. 401 là chưa xác thực hợp lệ, 403 là đã xác định danh tính nhưng không đủ quyền.

200 OK
201 Created
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
422 Unprocessable Content

401/403 phụ thuộc hợp đồng xác thực; thống nhất cách dùng trong cả ứng dụng. Không đưa lỗi cơ sở dữ liệu chi tiết hoặc bí mật vào response.

Tạo JSON trong PHP

json_encode chuyển dữ liệu thành JSON. Dùng JSON_THROW_ON_ERROR để phát hiện lỗi mã hóa; header Content-Type và status nên được đặt trước khi gửi nội dung.

<?php
$data = ["data" => [["id" => 1, "name" => "An"]]];
$json = json_encode($data, JSON_UNESCAPED_UNICODE | JSON_THROW_ON_ERROR);
echo $json; // {"data":[{"id":1,"name":"An"}]}

Trong controller web dùng header("Content-Type: application/json; charset=utf-8") và http_response_code(...) trước echo. Không đưa hash password hoặc token không cần thiết vào JSON.

Đọc JSON request

Với Content-Type application/json, đọc php://input rồi giải mã. Dữ liệu đầu vào không tin cậy: bắt JsonException, kiểm tra cấu trúc, kiểu và ràng buộc trước khi xử lý.

<?php
$raw = '{"name":"An"}';
try {
    $data = json_decode($raw, true, 512, JSON_THROW_ON_ERROR);
    if (!is_array($data) || !isset($data["name"]) || !is_string($data["name"])) {
        throw new InvalidArgumentException("Thiếu tên hợp lệ");
    }
    echo $data["name"];
} catch (JsonException | InvalidArgumentException $e) {
    echo "Dữ liệu không hợp lệ";
}

Trong server thực tế, $raw lấy bằng file_get_contents("php://input"); đặt giới hạn kích thước request và trả status lỗi phù hợp.

Thiết kế lỗi có thể kiểm thử

Một cấu trúc lỗi nhất quán giúp client hiển thị lỗi đúng trường. Cần phân biệt JSON sai cú pháp với dữ liệu hợp lệ về cú pháp nhưng không vượt validation theo quy định của API.

HTTP/1.1 422 Unprocessable Content
Content-Type: application/json

{"message":"Dữ liệu không hợp lệ","errors":{"email":["Email không hợp lệ"]}}

Không tiết lộ stack trace, mật khẩu, token hay cấu hình DB. Chuẩn hóa theo hợp đồng của ứng dụng, không bắt buộc dùng đúng hình dạng ví dụ này.

Git, Postman và kiểm thử

Git ghi lịch sử thay đổi. Postman giúp gửi request và lưu collection; test GET/POST/PUT/DELETE cho trường hợp thành công, ID sai, trường thiếu, email trùng và không đủ quyền.

git status
git diff
# Sau khi kiểm tra file, tự chọn và commit theo quy trình của bạn.

Không đưa .env, token hay collection chứa mật khẩu thật vào Git. Trước khi xóa dữ liệu trong test, dùng database thử nghiệm được phép xóa.

Bài tập theo lộ trình

  1. Triển khai 5 endpoint /api/students và /api/students/{id} cho GET, POST, PUT, DELETE; xác định status 200, 201, 400, 404, 422 theo từng tình huống.
  2. Tạo Postman Collection kiểm thử thành công và lỗi: JSON sai, thiếu tên, email trùng, ID không tồn tại, không có quyền; không lưu token thật trong collection.
  3. Hoàn thiện Student Management PHP MVC kết nối MySQL, xác thực dùng password_hash/password_verify, API và README; chỉ đẩy repo hoặc triển khai khi đã được cho phép.

Ghi đầu vào, kết quả mong đợi và thực tế; kiểm tra cả trường hợp rỗng và biên.
